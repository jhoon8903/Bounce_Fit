## 1. 확정된 방향과 현재 상태

- [DECISION] Android/iOS에 정식 출시할 게임을 새 프로젝트에서 만든다.
- [DECISION] BALL x PIT의 기능과 전투·성장 구조를 최대한 설계 기준으로 삼고, 너구리 대마법사와 숲 수호 컨셉을 주된 차별화 방향으로 삼는다. 시스템마다 새로운 차별 규칙을 만들기 위해 기존 방향을 변경하지 않는다.
- [DECISION] 사용자가 제시한 테마 레퍼런스는 동물의 숲이다. 인간들이 숲을 파괴하러 오고 캐릭터가 이를 막는 디펜스 로그라이크를 지향한다.
- [DECISION] 플레이어 캐릭터는 너구리 대마법사다.
- [DECISION] 별도의 방어선·숲 내구도를 관리하지 않고 너구리의 생존을 중심으로 전투를 판정한다. 사용자는 적의 탄막 공격이 존재하므로 생존에 집중하는 방식을 선택했다.
- [DECISION] 일반 구간을 생존한 뒤 마지막 보스를 처치하면 승리한다. 정해진 시간을 버티거나 구간을 통과하는 것만으로는 승리하지 않는다.
- [DECISION] 마지막 보스전을 포함한 한 판의 목표 길이는 약 5~10분이다. 즉시 실패한 런의 최소 시간이나 강제 종료 제한을 뜻하지 않는다. 강화 선택 시간 포함 여부는 미정이다.
- [DECISION] 런 중 레벨업하면 현재 선택 가능한 카드 전체에서 무작위로 3개를 제시하고 1개를 선택한다. 종류별 할당은 없다. 강화·패시브·신규 스킬을 각각 1개씩 보장하던 직전 안은 최신 사용자 선택으로 대체되었다.
- [DECISION] 레벨업 후보에는 새 마법 획득과 보유 마법 강화를 함께 넣는다. 구체적인 마법 종류·최대 강화 단계·등장 확률은 미정이다.
- [DECISION] 한 런의 보유 한도는 액티브 스킬 4개, 패시브 스킬 3개를 기준으로 한다. 사용자가 적정 규모로 제시한 값이며 실제 조합 수와 전투 가독성으로 검증한다.
- [DECISION] 기본 공격은 액티브 4칸 중 1칸을 차지한다. 기본 공격을 별도의 다섯 번째 액티브로 계산하지 않는다.
- [DECISION] 융합은 액티브 2개를 소모해 새로운 스킬 1개를 만들고 액티브 한 칸을 비운다. 조합 조건·시점·강화 계승과 기본 공격의 융합 가능 여부는 후속 확인한다.
- [DECISION] 액티브 스킬은 자동 발동한다. 별도 스킬 발동 버튼은 추가하지 않는다.
- [DECISION] 기본 공격도 강화할 수 있으며 `Ball 추가`가 강화 후보에 포함된다. 기본 공격은 액티브 1칸을 사용하고, 추가 Ball의 수·발사 방식·최대 단계는 미정이다.
- [DECISION] 적을 처치하면 경험치 구슬이 나오고, 너구리가 직접 주워 경험치를 얻어 레벨업한다. 처치 즉시 경험치를 자동 지급하는 방식은 아니다.
- [DECISION] 적은 여러 경험치 구슬을 드롭한다. 기본 구슬은 개당 1XP, 더 큰 구슬은 개당 10XP다. 적별 구슬 수와 등급 구성은 미정이다.
- [DECISION] 중간중간 다른 색상의 구슬이 등장해 더 많은 경험치를 준다. 고가치 구슬의 정확한 XP와 등장 빈도는 미정이다.
- [DECISION] 줍지 못한 구슬이 화면 아래로 지나가면 사라진다. 이후 구간에서 자동 회수하거나 경험치로 보상하지 않는다.
- [INFERENCE] 포근한 동물 마을·자연의 분위기를 지키는 경험으로 해석한다. 생활 시뮬레이션·마을 꾸미기를 포함하는지는 아직 결정하지 않았다.
- [DECISION] Bounce-Defense는 과거 1스테이지 과제 프로젝트이며 참고 자산이다.
- [DECISION] 고정 위치 전투에서 벗어나 캐릭터가 앞으로 진행하고 적의 탄막 공격이 존재한다.
- [DECISION] 전투 중 전후좌우를 직접 움직여 탄막을 피한다. 사용자 후속 답변으로 확인했다.
- [DECISION] 왼손 조이스틱으로 직접 조준하고, 오른손 조이스틱으로 전후좌우 이동한다. 최신 사용자 선택으로 기존 자동 조준 결정을 대체한다.
- [DECISION] 액티브 발동은 자동이다. [HYPOTHESIS] 기본 공격 역시 별도 버튼 없이 조준 중 연사하는 안을 유지한다. 조준 입력을 놓았을 때의 발사 지속 여부는 미확정이다.
- [DECISION] DOTS를 활용한 최적화 설계, 에셋 제작, 레벨 디자인 및 밸런스 자동화를 원한다.
- [DECISION] 가로 화면으로 제작한다. 최신 사용자 선택으로 기존 세로 화면 결정을 대체한다.
- [DECISION] 가로 화면 안에서 일정 속도로 자동 전진하는 종스크롤 게임이다. 너구리는 화면 안에서 전후좌우로 움직인다. 플레이어 입력으로 스크롤 속도나 방향을 바꾸지 않는다.
- [DECISION] 캐릭터의 정면은 보여줄 필요가 없다. 전방을 향한 상태로 백스텝·사이드스텝하며 뒷모습·좌우 뒤쪽 대각·측면 위주로 표현한다. 전후좌우 입력은 자동 진행 기준 위치에 대한 상대 이동이다. 전진 시 세부 애니메이션은 후속 검증한다.
- [DECISION] 조준 범위는 전방 160도다. 전방 중심에서 좌우 80도로 구체화한다.
- [HYPOTHESIS] 각도 기준은 스테이지 전방 축으로 두어 캐릭터 몸을 연속 회전해 후방 사격하는 것을 막는다.
- [DECISION] 사용자 첨부 이미지처럼 캐릭터의 뒤쪽 위에서 전방 바닥과 적을 내려다보는 3인칭 사선 구도를 목표로 한다. 진행은 자동 스크롤을 따르며 투영 방식과 시야 범위는 별도 검증한다.
- [OPEN] 2.5D는 검토 방향이다. 조이스틱 고정/유동 방식, 조준 해제 시 동작·사거리·반사 후 후방 처리, 수익화, 대상 기기, 제작 인력·기간은 미확정이다.
- [DECISION] 사용자가 시스템 레퍼런스로 지정한 게임은 BALL x PIT이다. 원작 내부 렌더링 구현은 확인하지 않았으며, 아래 기술 제안은 새 게임의 구현안이다.

[FACT] BALL x PIT의 공개 모바일 리뷰에는 터치 조준, 조작 변경, 작은 화면의 시인성, 저장 문제에 대한 사례가 있다. PunBall 공개 리뷰에는 성장 압박·난이도·공 회수에 대한 불만 사례가 있다. 표본이 제한적이고 과거 리뷰도 포함되므로 현재 전체 이용자의 불만 비율 또는 미해결 버그로 일반화하지 않는다.

[INFERENCE] 최소 기대는 읽히는 적탄, 납득 가능한 피격, 설명 가능한 강화 효과, 안정적인 중단·복귀다. 장르의 콘텐츠 양 경쟁보다 모바일 조작의 완성도를 먼저 검증한다.

[HYPOTHESIS] 한 문장 후보: **너구리 대마법사가 튕기는 자연 마법을 조합해 숲을 파괴하러 오는 인간들을 막는 종스크롤 디펜스 로그라이크.** 너구리 대마법사는 확정이며 자연 마법의 구체적인 형태는 추천안이다.

[DECISION] 차별화의 중심은 포근한 숲과 동물들, 너구리 대마법사, 인간의 파괴에 맞서는 테마와 표현이다. 시스템은 BALL x PIT을 최대한 기준으로 삼는다. [EXPERIMENT] 이 컨셉이 캐릭터 애착·전투 동기·재도전으로 이어지는지는 실제 플레이로 검증한다. 수익화는 광고 SDK 설치 여부와 별개로 사용자 결정이 필요하다.

### BALL x PIT 기능 매핑과 적용 기준

조사일 2026-09-28. [공식 Steam 소개](https://store.steampowered.com/app/2062430/BALL_x_PIT/)에서 반사 공 전투·공 조합, 거점 건설과 자원 생산·해금, 캐릭터별 고유 능력, 지역별 적·위험·보스를 확인했다. 현재 소개된 업데이트에는 새로운 공·패시브·진화 관련 콘텐츠와 보스 이후 계속하는 무한 모드도 있다. 아래 매핑은 원작 소스 코드나 상세 수치를 확인한 결과가 아니라 공개 기능 설명과 사용자 결정을 연결한 것이다.

| 기능 | 이 프로젝트 적용 | 상태 |
|---|---|---|
| 반사 공·다수 적 전투 | 너구리의 마법 구슬과 인간 침입자 | 코어 방향 확정. 개별 마법 표현·효과는 제안 |
| 런 중 성장·공/패시브 조합 | XP 구슬 수집, 유효 카드 무작위 3택1, 기본 공격 포함 액티브 4·패시브 3 | 사용자 규칙 우선 |
| 스킬 조합 | 액티브 2개 소모 → 1개 생성 → 한 칸 확보 | 사용자 확정. 원작 일반 융합/조합식 진화의 차이는 세부 검증 필요 |

### 숲 방어 테마 — 제안과 미결정

플레이어 정체성:

- [DECISION] 너구리 대마법사. 성격·나이·이름·외형 세부는 미정이다.
- [HYPOTHESIS] 후방 사선 구도에 맞춰 꼬리·로브·지팡이의 실루엣으로 정체성을 보여준다. 얼굴 표정에 의존하지 않고 귀, 자세, 지팡이의 빛과 작은 동작으로 감정을 전달한다. 꼬리 무늬 등 종의 해석은 아트 기준 제작 전에 확인한다.
- [HYPOTHESIS] 자연 마법 구슬을 기본 반사 공으로 표현하고 씨앗·수액·가시·덩굴·포자를 강화 테마로 비교한다. 후보를 한꺼번에 구현 범위로 확정하지 않는다.
- [EXPERIMENT] 지팡이·모자·꼬리·로브가 플레이어 피격 중심이나 다가오는 탄환을 가리지 않는지 확인한다. 지팡이 발사점과 조준 표시가 일치해야 하며, 좌우 반전 시 지팡이를 든 손이 바뀌는 문제를 검증한다.

| 기존 시스템 | 테마 적용 후보 | 기대하는 플레이 판단 |

| 반사 공 | 도토리·씨앗·수액 구슬 | 직격과 벽 반사 중 유리한 경로 선택 |

| 적 역할 | 벌목꾼·방패를 든 진입자·원거리 도구 사용자 | 접근하는 적과 위험한 탄막을 발사하는 적의 우선순위 비교 |

[HYPOTHESIS] 아트는 둥근 실루엣, 읽기 쉬운 얼굴·도구, 부드러운 색과 단순한 재질을 비교한다. 배경의 녹색과 자연 탄환이 섞이지 않도록 명도·윤곽을 분리한다. 도트 스타일은 확정하지 않았으며, 기존 전투 시점 레퍼런스와 새 아트 분위기를 구분한다. 인간 적은 과장된 작업자 캐릭터와 후퇴·장비 파손 연출을 후보로 둔다. 실제 이미지 생성은 아직 시작하지 않는다.

[DECISION] 캐릭터 생존 방식을 채택한다. 방어선 돌파에 따른 숲 내구도 감소는 제외한다. 숲을 지킨다는 목표는 전투의 배경과 구역 진행·결과에 연결한다.

- [HYPOTHESIS] 너구리의 체력이 소진되면 런 실패로 처리한다. 재시도·부활·런 밖 보상은 미확정이다.
- [DECISION] 승리 조건은 마지막 보스 처치다. 일반 구간의 생존·진행은 보스전에 도달하기 위한 과정이다.
- [HYPOTHESIS] 대표 런은 적 처치 → 경험치 구슬 획득 → 레벨업 3택1 강화 → 더 복잡한 전투 → 최종 보스 → 결과의 흐름으로 구성한다. 처치·구슬 수집을 통한 경험치 획득과 선택 방식은 확정이며, 드롭 경험치량·레벨 곡선·선택 중 정지 여부와 런 밖 보상은 미정이다.

### 5~10분 런 — 페이스 검증안

[DECISION] 목표 길이는 보스전을 포함해 약 5~10분이다. [HYPOTHESIS] 첫 대표 런의 조정 기준을 약 7분으로 잡되, 다음 시간표는 콘텐츠 약속이나 고정 타이머가 아닌 플레이테스트용 초안이다.

| 구간 | 임시 시간 | 경험 목표 |
|---|---|---|
| 진입·첫 선택 | 0~1분 | 이동·조준·반사 공격을 이해하고 첫 강화를 빠르게 경험 |
| 조합 형성 | 1~3분 | 다른 역할의 적을 만나 마법 강화의 차이를 확인 |
| 조합 시험 | 3~6분 | 적 배치와 탄막 조합이 복잡해지고 선택한 강화가 결과에 기여 |

[HYPOTHESIS — 재검토 필요] 초기 런당 강화 선택 5~7회 가설은 액티브 4칸·패시브 3칸 결정에 따라 재검토한다. 신규 획득만으로 선택을 소진하지 않도록 시작 구성·회수율·경험치량·레벨업 간격을 함께 검증한다. 선택 방식은 레벨업 3택1로 확정되었지만 횟수는 아직 확정하지 않았다.

### 레벨업 3택1 — 확정과 세부 추천안

- [DECISION] 레벨업마다 현재 선택 가능한 카드 전체에서 무작위 3개를 제시하고 1개를 선택한다. 보유 스킬 강화·패시브·신규 액티브의 개수는 보장하지 않는다. 같은 종류의 서로 다른 카드 3개가 등장할 수 있다.
- [HYPOTHESIS] 같은 선택 화면에서는 서로 다른 유효 후보를 제시한다. 최대 강화에 도달한 항목이나 적용 불가능한 후보를 제외하고, 후보가 부족할 때의 처리 규칙은 콘텐츠 구성과 함께 정한다.
- [DECISION] 기본 공격의 `Ball 추가`, 보유 스킬 강화, 패시브, 새 액티브가 공통 후보군에 들어간다. 고정된 강화 칸·패시브 칸·신규 칸은 없다. 보유 한도는 기본 공격을 포함한 액티브 4개·패시브 3개다. 융합 시스템은 채택하며 세부 규칙·패시브 중복 강화·최대 레벨은 미정이다.
- [HYPOTHESIS] 현재 획득·강화 가능한 카드만 필터링하고, 같은 선택 화면에서는 동일 카드를 중복 추첨하지 않는다. 기본은 카드별 동일 확률로 시작하되 등급 가중치·이전 등장 이력 보정은 아직 적용하기로 결정하지 않았다. 후보군 크기 때문에 종류별 등장 비율이 달라지는지 측정한다.

- [EXPERIMENT] 자동화에서는 콘텐츠 버전과 seed를 기록해 동일한 선택지 출현을 재현한다. 실제 선택률과 후보 제시율을 구분하고, 선택 후 전투 기여·보스 도달률을 함께 비교한다. 무작위 등장만으로 의미 있는 선택이나 균형이 보장되지는 않는다.

### 액티브 4칸·패시브 3칸 — 기준과 검증

- [DECISION] 액티브 보유 한도는 기본 공격을 포함해 4개, 패시브 보유 한도는 3개다. 기본 공격 외 액티브는 최대 3개를 추가 보유할 수 있다. 매 런에 반드시 모든 슬롯을 채워야 한다는 의미는 아니다.
- [DECISION] 액티브 스킬은 자동 발동한다. 기존 왼손 조준·오른손 이동 조작을 유지한다. 개별 스킬의 발동 주기·조건은 별도로 정의한다.
- [HYPOTHESIS] 액티브는 구슬·분열·덩굴 등 전투 효과를 만들고 패시브는 반사·발사 주기·획득 범위 등 지속 효과를 주는 역할로 구분한다. 구체적인 기술 목록은 미정이다.
- [DECISION] 자동 액티브를 위한 별도 발동 버튼은 추가하지 않는다. [HYPOTHESIS] 조준형 공격은 전방 160도를 따르도록 하고, 주변 범위나 유도 효과의 후방 허용은 기존 후방 공격 미결정 사항과 함께 정한다.
- [DECISION] 패시브는 신규 액티브·보유 스킬 강화와 함께 레벨업 공통 후보군에서 등장한다. 종류별 최소 제공 수는 없다.
- [HYPOTHESIS] 액티브 4칸 또는 패시브 3칸이 가득 차면 그 종류의 신규 획득 카드를 유효 후보군에서 제외하고, 남은 전체 후보에서 3개를 뽑는다. 보유 스킬 강화는 유효한 동안 남는다. 융합으로 액티브 한 칸이 비면 신규 액티브 획득 자격을 다시 평가한다. 최대 강화 등으로 전체 유효 후보가 3개 미만일 때의 대체 처리와 패시브 강화 가능 여부는 미정이다.
- [DECISION] 기본 공격은 액티브 1칸을 차지하며 `Ball 추가`로 강화할 수 있다. [OPEN] 추가량·발사 형태·최대 강화 단계를 정해야 한다. 수량 증가를 피해량 증가로 대체하거나 산탄/순차 연사 중 하나로 임의 확정하지 않는다.
- [EXPERIMENT] 기존 런당 5~7회 강화 선택 가설을 재검토한다. 예를 들어 액티브 1개로 시작하고 모든 스킬을 3택1에서 얻는다면 4+3칸을 채우는 데만 추가 신규 선택 6회가 필요하다. 7회 선택이면 강화에 남는 선택은 1회다. 따라서 슬롯을 채우는 선택과 집중 강화가 모두 의미 있도록 시작 구성·경험치 곡선·선택 횟수를 함께 조정한다. 슬롯 수를 줄이거나 강화 횟수를 늘렸다고 이미 확정하지 않는다.
- [EXPERIMENT] 액티브 4개가 겹칠 때 적탄 가독성, 효과 생성량, 개별 스킬의 기여를 확인한다. 강화를 자동화 평가할 때 피해량뿐 아니라 생존·구슬 회수·보스 처치 시간의 기여를 함께 비교한다.

### 스킬 융합 — 2개 소모·1개 생성 확정

- [DECISION] 스킬 융합으로 새로운 스킬을 만들 수 있다. 액티브 4칸의 기본 공격 슬롯 포함 결정과 함께 채택되었다.
- [DECISION] 액티브 A와 B를 소모해 융합 스킬 C 하나를 얻고 액티브 한 칸을 비운다. 빈 칸에 새 스킬을 획득해 조합을 이어갈 수 있다. 재료를 촉매로 남기는 안은 이번 결정으로 채택하지 않는다.
- [EXPERIMENT] 두 효과를 합치는 일반 융합과 특정 조합으로 고유 능력을 얻는 진화가 별도 규칙인지 원작을 확인해 정리한다. 원작 용어의 세부 구분을 확인하기 전에는 이 문서의 '융합'을 사용자가 확정한 2→1 규칙의 포괄 명칭으로 쓴다.
- [OPEN] 고정 조합식인지, 어떤 스킬이 재료인지, 필요한 강화 단계가 있는지, 융합 시점이 레벨업/보상/별도 UI인지, 기본 공격도 융합 가능한지, 강화 투자와 Ball 추가 효과를 어떻게 계승하는지 정해야 한다. 패시브를 자동으로 융합 재료로 가정하지 않는다.
- [EXPERIMENT] 5~10분 동안 재료 획득과 강화에 필요한 선택 수를 계산한다. 낮은 경험치 회수율에서도 융합 기회를 얻을 수 있는지, 재료를 기다리는 동안 의미 없는 선택이 반복되는지 확인한다. 융합 횟수·재료 단계·확률은 아직 고정하지 않는다.
- [EXPERIMENT] 융합 전후의 슬롯 수·효과·강화 상태를 명시적으로 비교한다. 재료 제거와 결과 생성은 하나의 처리로 다루고 중복 스킬 생성·재료 효과 잔존·후보 목록 갱신 누락을 검증한다. MVP에서 먼저 구현·검증한다.

### 경험치 구슬 — 획득 규칙과 검증

- [DECISION] 적 처치 시 여러 경험치 구슬을 생성한다. 너구리가 구슬을 획득할 때 각 구슬의 XP를 가산하며, 요구 경험치에 도달하면 레벨업 3택1 선택으로 이어진다. 기본 구슬 1XP, 큰 구슬 10XP, 다른 색의 고가치 구슬은 XP 미정이다. 모든 적이 모든 등급을 드롭한다고 가정하지 않는다.
- [HYPOTHESIS] 구슬은 적이 처치된 전투 위치에 떨어지고 자동 스크롤에 따라 화면에서 이동한다. 적 처치 위치와 구슬 수집 경로가 연결되어야 한다. 제자리에서 일정 시간 기다리는 것만으로 모든 구슬이 자동 획득되는 배치는 피한다.
- [HYPOTHESIS] 구슬에 가까이 접근하면 짧은 거리만 끌려오는 보조 흡수를 시험한다. 너구리를 구슬 중심에 정확히 겹쳐야 하는 부담을 줄이되, 멀리 있는 구슬까지 기본으로 자동 수집하지 않는다. 흡수 반경·획득 판정과 자석 능력은 미확정이다.
- [DECISION] 자동 스크롤로 화면 아래에 지나간 미획득 구슬은 소멸하며 경험치를 지급하지 않는다. 구간 끝·보스 직전 회수는 하지 않는다. [EXPERIMENT] 소멸 기준선은 실제 표시와 획득 가능 영역에 맞춰 정하고, 화면에서 아직 보이는 구슬이 먼저 사라지지 않는지 확인한다. 같은 프레임에 흡수·획득·소멸 조건이 겹칠 때의 우선순위와 중복 지급도 검증한다.
- [EXPERIMENT] 멀리서 적을 처치했을 때 접근 가능한 시간, 좌우 이동 비용, 적탄과 구슬의 시각적 구별, 화면 하단 엄지 가림을 확인한다. 회수 욕심으로 위험을 감수한 피격과 애초에 도달 불가능했던 구슬을 구분한다.
- [HYPOTHESIS] 드롭은 경험치량 데이터를 가진 개체로 관리하고 풀을 활용한다. 큰 구슬 10XP는 별도 드롭 등급이며 작은 구슬 10개가 자동 합쳐지는 규칙으로 해석하지 않는다. 인접 구슬 합치기는 수집 위치와 놓치는 양을 바꿀 수 있으므로 현재 기본 규칙에 넣지 않는다.
- [HYPOTHESIS] 적별 지급 경험치 예산을 먼저 정하고 여러 구슬로 분배한다. 예를 들어 총 15XP인 적을 작은 구슬 15개 또는 큰 구슬 1개와 작은 구슬 5개로 표현할 수 있다. 이는 구성 예시이며 적의 보상량 확정이 아니다. 여러 구슬을 줍는 감각과 개체 수를 함께 검증한다.
- [HYPOTHESIS] 고가치 구슬은 다른 색상과 함께 테두리·중심 문양·빛의 차이로도 구별한다. 위험한 적탄이나 마법 구슬과 혼동하지 않도록 형태와 움직임을 비교한다. 구체적인 색상·형태는 아트 테스트에서 정한다.
- [EXPERIMENT] 지급 경험치 총량과 실제 획득량을 분리해 기록한다. 평균·낮은 회수율에서도 첫 강화와 보스 도달 시 성장량이 적정한지 확인한다. 구슬 손실 때문에 약해져 더 많은 구슬을 놓치는 악순환을 점검한다. 여러 구슬 동시 획득 시 중복 지급·누락, 여러 레벨 상승 시 초과 경험치 보존·선택 순서도 검증한다.

[EXPERIMENT] 전투 시간·강화 선택 시간·보스 시간을 분리해 기록하고 실제 총 플레이 시간이 5~10분 목표에 들어오는지 확인한다. 첫 선택까지의 시간, 처음 조합을 활용한 순간, 보스 도달 시 선택의 영향, 재도전 의사를 관찰한다. 기존 3분 전투 프로토타입은 조작 검증용으로 유지하며 완성 런 길이로 혼동하지 않는다.

## 4. 2.5D 표현 추천 — 아직 미확정

[HYPOTHESIS] **평면 전투 시뮬레이션 + 원근 카메라 + 단순 3D 지형 + 2D 캐릭터 표현**을 우선 비교한다.

- 전투 좌표는 XZ 평면의 2축이다. 높이(Y)는 우선 연출에만 쓴다.
- 바닥·벽은 간단한 메시로 만들고, 캐릭터는 카메라 방향에 맞춘 스프라이트 또는 쿼드를 비교한다. 공·적탄은 작은 메시/쿼드를 대량 렌더링한다.
- 원근을 약하게 시작해 먼 적탄이 지나치게 작아지거나 화면상 간격이 좁아지는지 확인한다. 고정 각도의 직교 카메라도 비교 기준으로 둔다.
- 그림자·바닥 표식과 실제 충돌 중심을 맞춘다. 연출상 점프 때문에 피격 높이를 오해하게 만들지 않는다.
- 터치 좌표는 카메라에서 전투 평면으로 변환한다. 화면 좌표를 그대로 월드 좌표로 쓰지 않는다.
- 자동 진행 위치와 플레이어의 화면 내 상대 위치를 구분한다. 카메라 진행은 오른손 이동 입력을 따라가지 않는다. 앞·뒤·좌·우 이동 한계와 전방 시야를 검증하며, 화면 경계에서의 정지·충돌 처리 수치는 미정이다.

### 일정 속도 종스크롤 — 확정과 후속 규칙

- [DECISION] 전투 진행 중 화면은 일정 속도로 전진한다. 전진·후퇴 입력은 화면 안의 상대 위치를 바꾸며 스테이지 진행을 가속하거나 되돌리지 않는다.
- [HYPOTHESIS] 오른손을 놓으면 화면 내 상대 위치를 유지한다. 자동 진행 기준 위치를 따라가므로 입력이 없다고 화면 아래로 밀려나지는 않는다.
- [HYPOTHESIS] 스테이지 진행 거리와 너구리의 상대 위치를 분리해 관리한다. 카메라를 이동시키거나 주변 지형을 반대 방향으로 이동시키는 구현 중 하나를 일관되게 사용한다. 충돌·발사·탄속에서 스크롤 속도가 이중 적용되지 않도록 검증한다.
- [HYPOTHESIS] 적 등장과 구간 전환은 진행 거리 기준 이벤트로 저작한다. 일정 속도 구간에서는 시간으로 환산할 수 있지만, 입력 위치와 무관하게 같은 웨이브를 재현할 수 있어야 한다.
- [OPEN] 전방에서 등장한 적이 플레이어를 지나친 후의 행동·제거 시점과 적탄 수명은 미정이다. 별도 숲 피해를 주지는 않는다. 화면 밖 후방의 예고 없는 공격을 피하고, 반사 공의 정상적인 귀환과 별도로 처리한다.
- [OPEN] 보스전·강화 선택·일시정지 중 스크롤을 계속할지는 아직 정하지 않았다. 일반 전투의 일정 속도 결정을 임의로 보스 정지나 속도 증가로 바꾸지 않는다.

### 캐릭터의 입체 표현 — 검토 중

[DECISION] 사용자 설명과 첨부 화면으로 목표 시점은 후방 상단에서 전방을 내려다보는 사선 구도로 구체화되었다.

[FACT — 첨부 이미지 관찰] 플레이어의 머리 윗면과 뒷모습, 적의 윗면·앞면, 받침대의 두께, 바닥 그림자와 앞뒤 가림이 보인다. 이 입체감은 최종 화면에 대한 관찰이며 실제 3D 모델 사용 여부나 정확한 카메라 투영·각도는 정지 이미지로 판정하지 않는다. 참고: 사용자 첨부 `Screenshot 2026-09-28 at 4.15.20 AM.png` (임시 파일이므로 이 설명을 장기 기록으로 남김).

[HYPOTHESIS] 카메라는 스테이지 진행 방향에 대해 각도를 고정하고 자동 진행에 맞춰 전장을 보여준다. 왼손 조준으로 캐릭터가 돌아도 카메라까지 회전시키지 않아 탄막·벽·이동 방향이 안정적으로 읽히게 한다. 첨부된 이미지의 세로 비율을 화면 방향 결정으로 해석하지 않으며, 확정된 가로 화면에 구도를 재배치한다.

[OPEN] 이 시점을 표현하는 방향별 2D 캐릭터와 실제 3D 캐릭터 중 구현 방식은 아직 결정하지 않았다. 원작의 내부 제작 방식은 확인하지 않았다.

| 후보 | 표현 | 제작·검증 요소 |
|---|---|---|
| 단일 2D 이미지/애니메이션 | 평면 이미지를 카메라에 보이게 배치하고 원근·접지 그림자로 깊이 표현 | 방향별 옆면·뒷면이 생기지는 않음. 조준 방향 표시를 따로 검증 |
| 방향별 2D 스프라이트 | 뒷모습·좌우 뒤쪽 대각·측면에 가까운 모습으로 전방 160도 표현. 정면 제외 | 방향 수 × 동작 × 프레임 수만큼 이미지·아틀라스 비용 증가. 방향 경계의 튐·비대칭 장비 검증 |
| 실제 3D 모델 | 카메라와 캐릭터 회전에 따라 실루엣·가려짐·빛이 연속적으로 변화 | 모델링·리깅·애니메이션과 대량 캐릭터 렌더링 경로 검증 |

[HYPOTHESIS] 전방 160도·후면 중심 표현으로 범위가 좁아져 3D 지형 + 제한된 방향별 2D 캐릭터를 우선 추천한다. 대표 포즈 후보는 뒷모습, 좌우 뒤쪽 대각, 좌우 측면에 가까운 모습의 5개다. 먼저 뒷모습·좌우 대각 3개로 전환을 검증하고 필요하면 측면 2개를 더한다. 포즈 수는 조준 해상도가 아니며 발사 방향은 160도 안에서 연속적으로 바뀐다. 카메라 회전·클로즈업·입체 장비 교체가 핵심으로 추가되면 실제 3D를 재비교한다.

[HYPOTHESIS] 3D 원본을 만든 뒤 여러 방향으로 렌더해 스프라이트로 사용하는 제작 경로도 있다. 방향·애니메이션의 일관성을 얻을 수 있지만 3D 제작 비용과 스프라이트 용량을 함께 고려해야 한다.

[DECISION] 후퇴할 때 돌아서지 않고 백스텝, 횡이동할 때 사이드스텝한다. [HYPOTHESIS] 하체는 전방 지향을 유지하고 상체·무기·발사 표시가 허용 범위 안에서 조준을 표현한다. 몸 전체를 조준각과 일대일로 회전시키지는 않는다. [EXPERIMENT] 상하체 분리와 전체 프레임 방식의 제작 비용·접합 어색함을 비교한다. 비대칭 무기·조명은 단순 좌우 반전으로 깨질 수 있으므로 검증한다.

[FACT] 빌보드는 카메라를 향하는 2D 표현이다. 그 자체가 새로운 측면/뒷면을 만들어 주지는 않는다. [Unity 빌보드 개념](https://docs.unity3d.com/6000.0/Documentation/Manual/2d-images-lod.html). 프로젝트 구현이 해당 BillboardRenderer 컴포넌트를 그대로 사용한다는 뜻은 아니다.

조작 결정: **가로 화면, 왼손 조준 조이스틱, 오른손 이동 조이스틱, 액티브 자동 발동**이다. 이전의 세로 화면·자동 조준 안을 대체한다. 조준 해제 시 동작은 미정이다.

### 가로 화면과 두 조이스틱 — 세부 추천안

- [DECISION] 왼쪽 하단 조이스틱은 공의 발사 방향을, 오른쪽 하단 조이스틱은 전후좌우 이동을 담당한다. 양손 배치는 사용자가 지정한 그대로 유지한다.
- [HYPOTHESIS] 이동 방향과 조준 방향을 독립시킨다. 뒤로 피하면서 앞을 쏘거나 옆으로 이동하며 벽을 조준할 수 있도록 한다. 가까운 적 자동 선정은 기본 조준 규칙에서 제외한다.
- [DECISION] 직접 조준은 전방 기준 -80도~+80도다. [HYPOTHESIS] 전투 평면에서 각도를 제한하고 표시선과 발사 모두 같은 방향을 사용한다. 원근 투영으로 화면상 각도는 다르게 보일 수 있다. 범위 밖 입력은 경계각으로 제한하는 안부터 시험하되, 정확히 뒤쪽을 가리킬 때 좌우 경계 사이에서 튀지 않도록 마지막 유효 방향을 활용한다.
- [OPEN] 후방 공격 금지가 발사 방향에만 적용되는지 반사 이후에도 적용되는지는 미확정이다. 초기 추천은 발사 방향만 제한하고 반사 궤적은 유지하는 것이다. 반사 후에도 후방 진입을 막으려면 회수선·소멸 등 별도 규칙을 정한다.
- [HYPOTHESIS] 별도 발사 버튼 없이 조준 중 자동 연사한다. 왼손을 놓으면 마지막 방향을 유지해 연사할지 발사를 멈출지는 실험한다. 오른손을 놓으면 이동을 멈춘다.
- [HYPOTHESIS] 조준 방향 표시선은 짧고 명확하게 표시한다. 화면에 보이는 방향과 실제 전투 평면의 발사 방향이 일치하도록 카메라 투영을 고려한다. 고정/유동 조이스틱, 데드존·감도·최대 반경은 실기기에서 정한다.
- [HYPOTHESIS] 자동 진행하는 카메라는 플레이어의 이동 가능 영역과 전방 적을 함께 보여주고, 두 엄지가 가리는 하단 모서리에 중요한 피격 정보가 몰리지 않게 구성한다. 플레이어의 화면 내 이동 범위는 미확정이다.
- [EXPERIMENT] 멀티터치가 각 조이스틱에 안정적으로 배정되는지 확인한다. 손가락이 중앙을 넘거나 다른 손을 먼저 떼어도 담당이 바뀌지 않아야 한다. 일시정지·앱 포커스 상실·터치 취소 때 남은 이동/발사 입력을 해제한다.
- [EXPERIMENT] 가로 화면의 좌우 시야와 짧아진 세로 시야를 함께 검증한다. 화면비별로 적 활성 범위·반사 벽·전방 예고 시간이 달라져 난이도가 흔들리지 않게 한다. 양손 조작 중 탄막 회피와 원하는 반사각 조준을 동시에 수행할 수 있는지가 핵심이다.
- [HYPOTHESIS] 이미 발사된 기본 공은 조준 변경에 따라 꺾이지 않고 기존 궤적과 충돌 반사 규칙을 유지한다. 유도 공은 별도 능력 후보로 둔다.

대안의 강점: 순수 2D/직교 화면은 탄막 간격·충돌 읽기가 쉽고 기존 자산 재사용이 편하다. 완전 3D는 카메라 회전·지형 높이·캐릭터 애니메이션 자유도가 높다.

추천의 반증 조건: 원근 때문에 플레이어가 피격 위치를 지속적으로 오판하거나, 높이·회전이 핵심 재미로 필요해지면 표현 구조를 다시 고른다. 2.5D라는 이유만으로 성능이나 제작비 절감을 보장하지 않는다.

## 5. DOTS 역할과 기술 검증

아래는 설계 후보이며 아직 구현 계약이 아니다.

| 영역 | 권장 담당 |
|---|---|
| 대량 공·적탄 이동, 수명, 발사 패턴 | ECS + Burst/Jobs |
| 충돌 후보 검색, 반사·피해·상태이상 | ECS의 평면 시뮬레이션 |
| 웨이브·런 진행, 런타임 전투 데이터 | ECS/순수 데이터 중심 |
| UI, 메뉴, 카메라, 소리, 상점·플랫폼 연동 | GameObject 및 일반 C# |
| 레벨·적·공·강화 저작 | ScriptableObject/편집기 → 검증 → 런타임 데이터 |
| 대량 시각 표현 | Entities Graphics 또는 별도 인스턴싱 경로를 실기기 비교 |

[FACT] [설치된 계열의 Entities Graphics 공식 요구사항](https://docs.unity3d.com/Packages/com.unity.entities.graphics@1.4/manual/requirements-and-compatibility.html)은 URP에서 Forward+를 명시한다. Android는 Vulkan 또는 OpenGL ES 3.1 이상, iOS는 Metal 조건이다. 현재 2D Renderer를 그대로 두고 Entities Graphics 대량 렌더링이 준비됐다고 볼 수 없다. ECS 시뮬레이션 사용과 Entities Graphics 채택은 별개 결정이다.

[HYPOTHESIS] 초기 충돌은 원/박스와 쓸림(sweep) 판정, 공간 격자 후보 검색을 우선 검토한다. 모든 공과 모든 적을 매 프레임 비교하지 않는다. 고속 탄환의 관통 누락, 같은 프레임 여러 번 반사, 겹친 적, 이동 표적을 반드시 검증한다. 복잡한 지형 물리가 필요해지면 Unity Physics와 비용을 비교한다.

- 충돌 결과는 이벤트로 모아 피해·사망·연쇄 효과 순서를 정의한다. 다중 작업이 같은 적 HP를 동시에 쓰지 않도록 한다.
- 빈번한 구조 변경·할당을 줄이고 풀 또는 enable 상태를 활용하되 기존 풀의 세션 초기화와 상태 잔존을 점검한다.
- 공마다 GameObject를 동기화하는 구조는 피한다. 효과·데미지 숫자·사운드에는 별도 출력 한도를 둔다.
- 증식·분열·연쇄 공격에는 수명, 세대, 동시 활성량 규칙을 둔다. 과부하 시 적탄을 몰래 지우는 식으로 전투 규칙을 바꾸지 않는다.
- 고정 timestep, seed, 안정적인 처리 순서, 콘텐츠 버전, 입력 기록을 준비한다. 이것만으로 Android/iOS 간 부동소수점 결과가 완전히 같아지는 것은 아니다.

[EXPERIMENT] 대상 기기를 정한 뒤 Android 저사양/중간급과 iPhone에서 동일 시나리오를 측정한다. 임시 목표는 60fps(16.7ms 프레임 예산)이며, 지원 하한과 30fps 옵션은 미정이다. 적·아군 공·적탄을 단계별로 늘리고 최악의 조합을 재생한다. CPU/GPU 시간, p95/p99 프레임 시간, GC, 메모리, 15~20분 후 발열 영향을 측정한다. 결과 전에는 최대 개체 수를 약속하지 않는다. DOTS는 투명 효과의 오버드로우나 GPU 병목을 자동으로 해결하지 않는다.

## 6. 에셋·레벨·밸런스 제작 순서

### 에셋

[HYPOTHESIS] 확정된 가로 화면에서 카메라 구도를 회색 도형으로 먼저 검증한다. 그 다음 플레이어 1종·적 1종·공·적탄·바닥 한 세트를 실제 화면에 배치해 기준을 잠근다. 대량 생성은 그 뒤다.

- 화면상 최소 크기, 원본 해상도, 단위당 픽셀, 피벗·발 접지점, 시점, 광원, 프레임 수, 알파, 아틀라스·모바일 압축을 규격화한다.
- 아군 공/위험한 적탄/배경 효과를 색뿐 아니라 윤곽·모양·움직임으로 구분한다.
- 캐릭터를 스프라이트로 표현해도 DOTS 렌더링 경로에서는 아틀라스 UV 기반 쿼드 등을 별도로 검증해야 한다.
- 실제 게임 이미지 생성·수정 작업에서는 프로젝트 지침에 따라 `game-asset-pipeline`을 사용한다. 이번 검토에서는 이미지를 생성하지 않았다.

### 레벨

[HYPOTHESIS] 수작업으로 좋은 전투 구간 몇 개를 만든 다음 검증된 구간을 제약 조건으로 조립한다. 처음부터 완전 무작위 생성에 의존하지 않는다.

작성 단위 후보: `Encounter → SpawnGroup → AttackPattern → Reward`. 일정 속도 종스크롤에 맞춰 진행 거리 기준 스폰·구간 이벤트를 추천한다. 위험도 예산은 적 수 외에도 발사 빈도, 탄속, 조준·추적 여부, 사각, 회피 경로 폭과 예고 시간을 포함한다. 자동 검사는 초기 진입 피격, 겹침, 화면 밖 즉시 공격, 스크롤·이동 속도·반응 시간을 고려한 탈출 경로를 탐지한다. 격자상 빈 칸이 있다고 사람이 회피 가능하다고 단정하지 않는다.

### 밸런스 자동화

`버전이 있는 전투 데이터 → 실제 게임과 동일한 시뮬레이션 → 고정 seed 묶음/입력 재생/여러 실력의 봇 → 결과 비교 → 사람 플레이테스트`를 추천한다.

자동 수집: 처치 시간, 피격 위치·원인, 클리어 시간·성공률 분포, 빌드별 피해/생존 기여, 무한 증식, 스폰 정체, 프레임 비용. 후보 빌드 간 동일 시드 비교와 실패 리플레이를 남긴다. 봇은 지연·조준 오차·회피 능력을 달리하고, 한 봇에만 최적화된 수치를 피한다. 재미·시인성·공정성의 최종 판단은 사람 플레이가 필요하다.

## 7. 첫 실험과 후속 게이트

초기 검토 당시의 실험 후보 기록이다. 이후 사용자의 구현 요청으로 9절의 MVP 범위를 적용한다.

| 후보 | 확인할 것 | 한계 |
|---|---|---|
| 카메라·판정 샌드박스 | 원근·적탄·접지점이 일치하는가 | 전투의 재미를 판정하지 못함 |
| 3분 전투 구간 — 추천 | 이동/공 반사/적탄 회피가 함께 성립하는가 | 장기 성장·유지 검증 아님 |
| 콘텐츠 많은 축소 런 | 보상·성장 루프 | 현재는 조작 불확실성을 콘텐츠가 가릴 수 있음 |

[EXPERIMENT] 추천 구간의 임시 범위: 플레이어 1종, 잡몹 2종, 적탄 패턴 2종, 반사 공 1종, 구별되는 강화 선택 3개, 끝이 있는 짧은 구간. 수치는 제작 약속이 아니라 최소 시험 후보다.

진짜여야 하는 것: 실기기 터치, 이동·발사·반사·피격, 최소 구별 가능한 시각/소리 피드백. 임시여도 되는 것: 캐릭터 외형·배경 장식. 제외: 거점 건설, 장비 경제, 대량 레벨, 광고/결제 흐름.

주 가설: 플레이어가 오른손으로 탄막을 피하면서 왼손으로 반사각을 조준하고 공격의 성과를 읽을 수 있다.

긍정 신호: 피격 원인을 설명하고, 재시도에서 경로나 발사 위치를 바꾸며, 요청 없이 다시 시도한다. 실패 신호: 원근·손가락 가림 때문에 반복적으로 오판하거나, 두 조이스틱을 동시에 조작하기 어렵거나, 화면의 조준 표시와 실제 궤적을 다르게 느끼거나, 반사각 선택에 의미 있는 차이가 없다. 온보딩·버그·프레임 저하와 규칙 자체의 실패를 분리한다. 대상 플레이어·인원·반복 예산·통과 기준은 다음 기획에서 합의한다.

순서: 대표 세션 구체화 → 가로 화면의 카메라/왼손 조준·오른손 이동 실험 → 작은 전투 프로토타입 및 기기 측정 → 관찰 증거를 반영한 MVP 계획 → 대표 에셋과 제작 파이프라인 → 레벨/밸런스 자동화 확장 → 출시 준비. 출시 단계에서 저장/중단 복귀, 기기 QA, 선택한 수익화와 플랫폼 연동, 배포 요구사항을 별도 확정한다.

## 9. 첫 플레이어블 MVP — 2026-09-28

[DECISION] MVP를 먼저 제작하며 적 및 Ball 이미지는 Bounce-Defense에서 재사용한다. 원본 파일은 변경하지 않고 PNG와 Unity importer metadata를 복사했다. 인간 침공자 아트는 후속 교체 대상이다.

실행 씬: `Assets/Projects/MVP/ForestMvp.unity`. Unity 메뉴 `Bounce Fit/MVP/Create or Open Playable Scene`으로 열고 Play. 기존 BootScene/Addressables 진입과 분리된 MVP 씬이며 빌드 목록 첫 항목이다.

실제 구현 범위:
- 가로 화면, 왼손 조준/오른손 이동, 자동 발사, 전방 ±80° 제한, 일정 속도 종스크롤.
- 원근 카메라 + 3D 바닥/임시 너구리 + 기존 적/Ball 빌보드 스프라이트.
- 기본 반사 Ball, 화염 범위 피해, 빙결 둔화, 폭풍 관통, 빙염 융합.
- 적의 조준탄, 예고 색상, 접촉 피해, 체력/무적 시간, 패배·재시작.
- 여러 XP 구슬, 근거리 자석, 직접 수집, 아래로 지나간 구슬 제거.
- 레벨업 시 전체 자격 후보에서 중복 없이 무작위 3장; 전투 일시정지; 연속 레벨업 처리.
- 기본 포함 액티브 4칸 / 패시브 3칸, 슬롯·최대 레벨 조건 검사, 2개 재료를 1개 융합 스킬로 교환.
- 최종 보스 처치 승리. 일반 타이머 종료나 보스 소멸만으로 승리하지 않음.

[PROVISIONAL] 첫 수치: 일반 구간 360초 후 보스, 체력100, 기본 Ball1개/피해10, 작은 XP1·큰 XP10·보라 XP25, 첫 레벨업8XP 후 요구량+5, 기본 Ball최대6, 일반 스킬/패시브 최대5. 화염Lv2+빙결Lv2이면 융합 카드 후보 추가. 융합 후 두 재료는 재등장하지 않음. 선택 시간이 전투 시계에 포함되지 않는다. 모든 수치는 검증 후 변경 가능하다.

개발용 단축 런은 보스45초이며 일반 런과 별개다. 에디터/Development Build에서만 XP 추가·보스 즉시 등장·단축 런 버튼을 표시한다. 릴리스에는 개발 버튼을 넣지 않는다.

구조: `MvpGame`이 입력/고정60Hz 호출/정지를 관리하고 `MvpCombat`은 전용 ECS World를 소유한다. 이동은 Burst IJobEntity로 병렬 처리한다. 현재 충돌·피해·스폰은 메인 스레드 EntityManager 경로이고 스냅샷을 pooled SpriteRenderer로 표시한다. 이는 전체 DOTS 최적화 완료 상태가 아니다. 광역 충돌 후보 탐색, 구조 변경 배치, 인스턴싱 및 실기기 프로파일링은 후속 단계다. 기존 EntityPool 샘플의 managed 문자열 Burst 오류는 예제의 자동 생성을 끄고 main-thread 예제로 정정했다.

제외: 마을/영구 성장, 수익화, 저장/중단 복귀, 최종 캐릭터/적 아트, 대량 레벨, 출시 서명/스토어 등록. 에디터 실행·규칙 자동 테스트와 실제 폰 검증을 구분한다.

### Ball 반사·회수 수정 — 사용자 플레이 피드백
